# AI 标准表转换 · 列名映射 PoC（T2）

验证一件事：**「乱表头 → 官方标准表」的列名对齐，靠「规则层 + DeepSeek 兜底 + 代码校验」三层能不能做稳，以及规则层单独能扛多少。**

配套方案说明见对话里的《DeepSeek 接入评估》；本目录是可跑的证据，不是文档。

## 先说清楚不覆盖什么

- ✅ **拍照识别（视觉）**：`src/ocr_table.py` 用 `deepseek-flash`（该模型 `input_modalities` 含 `image`）把表格照片读成「表头 + 数据行」，之后**复用本目录同一套映射链路**。口径与限制见下文「照片链路」。
- ❌ **行级数据改写与清洗**：本 PoC 只做「列 → 标准字段」。行级清洗（金额归一、日期归一）应当由代码按映射批量执行，不交给模型。
- ❌ **多 sheet 归类、多级表头、合并单元格**（T1）：未做，`--sheet` 需手工指定。
- ❌ **视觉 / 交互**：与原型 UI 无关。

## 在原型里实测（接真 Excel + 真 DeepSeek）

```powershell
cd ai-server
python server.py            # 默认 http://127.0.0.1:8787
```

然后浏览器打开 **http://127.0.0.1:8787/**，走「上传表格 → 本批清单 → 标准表转换」，
在「上传表格」页点某类的上传按钮选一个真实 Excel（`ai-server/samples/` 里有两张乱表头样本可用）。

为什么必须过这层桥，而不是页面里直接 fetch DeepSeek：

- 浏览器直连 `api.deepseek.com` 会被 **CORS** 拦掉，请求根本发不出去；
- Key 写进前端 JS 等于公开给所有能打开页面的人。

所以 `RTA开店流程与数据导入/ai-bridge.js` 只调同源的 `/api/ai/*`，Key 只存在服务端
（`ai-server/.env.local` 或环境变量 `DEEPSEEK_API_KEY`，`.env.local` 已在 `.gitignore` 里）。

**没起桥时不会坏**：直接双击 `index.html` 打开，选文件会退回原来的演示数据，并用 toast 说明。

⚠️ **GitHub Pages（`xdean-designer.github.io/data/`）上调不了 AI**：Pages 是纯静态托管，
`/api/ai/health` 实测 404，且浏览器直连 DeepSeek 会被 CORS 拦。页面能打开、不报错，
但只会走演示数据，`AI 实测明细` 与 `AI 推断` 标都不会出现。

### 手机上测（同一 Wi-Fi）

```powershell
python server.py --lan      # 绑 0.0.0.0，启动时会打印手机该开的地址
```

手机与电脑连同一 Wi-Fi，开程序打印的 `http://<内网IP>:8787/`。
真机 UA 会自动进手机预览（`mobile-preview.js` 按 UA 判定，不用手动加 `?mobile=1`）。

手机连不上时按顺序查：① 是否同一网段；② 电脑防火墙是否放行该端口；③ 电脑是否睡眠。

### 照片链路（视觉）

拍照页在**真实模式**下才会把照片送去识别（演示模式的快门只落 canvas 样张）。

```powershell
python server.py --lan
```

- 桌面端：拍照页按快门取实时取景帧；或点「照片」选本地图片。
- **手机端**：`http://<内网IP>:8787` 是**非安全上下文**，`getUserMedia` 不可用，实时取景拿不到
  ——此时按快门会提示改用「照片」按钮（`input[type=file][capture=environment]`，直接调系统相机）。
  要在手机上用实时取景，得走 `https`（自签证书需手动信任）。
- 连拍：同一类别的多张照片按**表头指纹**（`dict_match.norm` 归一后拼接）分组，
  指纹相同的合并成一张表并累加行，不同则各成一张表。
- 不猜：看不清的单元格留空（prompt 硬约束），表头没读到的照片**整张拦下**并提示重拍，
  不拿第一行硬当表头。

`/api/ai/convert` 的入参是 `{"category": "...", "files": [...], "photos": [{"name","data"}]}`，
`data` 为 base64 或 dataURL；`files` 与 `photos` 可同批，返回的每个表带
`source`（`excel` / `photo`）与照片表专属的 `ocr`（调用次数 / 延迟 / tokens）。

### 转换屏上能直接看到什么

走实测时，`import-convert` 屏底部会多出一块「AI 实测明细」：

- 每个 sheet：识别成了哪套标准模板、表头在第几行、几列对上了几列；照片表显示「照片 N 张」并额外给一行识别口径（prompt 版本 / 张数 / 延迟 / tokens）；
- 逐列的 `源列 → 标准字段 · 置信度 · 来源（词典 / AI / 拦截）· 依据`；
- **原表缺必填列** 与 **非必填未命中** 分开列，避免把「AI 没认出来」和「原表根本没这列」混为一谈；
- 模型调用次数、token、延迟；词典全命中时显示「未调用模型」。

概览屏里由模型推断出来的字段会打 `AI 推断` 标；`需修正 / 建议确认` 仍由原型的
`checkProblems()` 判定，模型不参与判级。

## 怎么跑

```powershell
cd ai-server

# 1) 结构自检：不花钱，验证管线通不通
python tools/selftest.py

# 2) 离线基线：只跑规则层，不需要 API Key
python src/run.py

# 3) 接模型：规则层没命中的列才送 DeepSeek
$env:DEEPSEEK_API_KEY = "sk-..."
python src/run.py --online

# 4) 想看模型裸能力（全表都送，不靠词典）
python src/run.py --online --llm-scope all

# 5) 只跑某个用例
python src/run.py --case hard_longtail --online
```

报告落在 `out/report.md`（含逐列明细），原始结果在 `out/details.json`。

## 当前结果

已跑两种模式，都是 `python src/run.py` 的真实输出（`out/report.md`）：

| 用例 | 列数 | 规则层 准确/召回 | 规则层+模型 准确/召回 |
|---|---|---|---|
| real_members_export（真实 1433 行导出） | 12 | 100% / 100% | 100% / 100% |
| messy_members_full（构造） | 15 | 100% / 92.3% | 100% / 100% |
| messy_price（构造） | 8 | 100% / 100% | 100% / 100% |
| messy_card_savings（构造） | 10 | 100% / 100% | 100% / 100% |
| **hard_longtail（构造，故意不进词典）** | 10 | 100% / **30%** | 100% / **100%** |
| 合计 | 55 | 100% / 82.6% | **100% / 100%** |

必填列召回 **75.0%（15/20）——仅离线模式**；接模型后为 100%。

三点要注意：

1. **前四个用例的 100% 没有信息量**：`messy_*` 的列名本来就照同义词词典写的，属于自证。
2. **`hard_longtail` 才是真实世界的形状**：列名换成 `客人称呼 / 联络号码 / 充值本金 / 尚余金额 / 卡到期` 之后，规则层只有 30% 召回；接上模型后 100%。这量化了「规则层省成本、模型兜长尾」的分工。
3. **一个踩到的坑**：早期版本里「卡面编号」被 2 字同义词「编号」包含匹配成「序号」，还给了 1.0 置信度，于是这一列**根本不会送给模型复核**，错误被固化。修法是「2 字及以下同义词不参与包含匹配」（`dict_match.MIN_CONTAIN_LEN = 3`）。这条比任何 prompt 技巧都值钱——**规则层的过度自信会屏蔽模型的纠错能力**。


## 三层分工（本 PoC 的核心主张）

| 层 | 负责 | 不负责 | 为什么 |
|---|---|---|---|
| ① 规则层 `dict_match.py` | 已知别名的精确/包含匹配、黑名单拦截 | 长尾写法 | 0 成本、0 延迟、结果可复现 |
| ② 语义层 `llm.py` | 规则层没吃掉的列 | 生成数据值、判级 | 只允许它选字段、给置信度和依据 |
| ③ 校验层 `validate.py` | schema 校验、自创字段拦截、阈值判级 | —— | 同一文件两次跑结论必须一致 |

映射到原型的数据模型（正好一一对应，不用改结构）：

- 源值 → `f`（原表原值，模型一个字都不许改）
- 模型判定的字段 → `aiFields`（并在 UI 上打「AI 推断」标）
- 代码算出的问题 → `problems`（**需修正 / 建议确认** 全部由 `validate.decide()` 判，不交给模型）

## 指标口径

| 指标 | 定义 | 为什么盯它 |
|---|---|---|
| 准确率 precision | 我们挂的列里挂对的比例 | 错挂会让数据写进错字段，最贵 |
| 召回 recall | 该挂的列里挂上的比例 | 漏挂只是让用户在概览里手工补，成本较低 |
| 错挂 | 挂了但字段不对 | |
| **误挂** | 本该拒识（如「支付方式」）却挂上了 | 最危险：静默污染数据 |
| 必填列召回 | 必填字段有没有挂上 | 直接影响「需修正」行的数量 |
| 规则层单独命中 | 零成本解决的部分 | 决定 token 成本和确定性 |

判级阈值固定 `0.8`，见 `validate.CONF_THRESHOLD`，改动请同步 PRD。

## 怎么加你自己的乱表

```powershell
python tools/add_case.py "D:\某店会员表.xlsx" --target member --sheet 会员 --id store_a
```

它会打出表头 + 4 行样本的 JSON 片段，**你手工把 `truth` 补成「每个源列 → 标准字段」**，再粘进 `golden/cases.json`。不补 truth 就粘进去，分数是假的。

> 真实文件先脱敏：姓名、手机号、卡号。

## 已知限制（别当成结论用）

1. 评测集只有 **5 个用例**（1 真实 + 4 构造），**没有统计意义**，只能用来发现失败模式。
2. 构造样本是我按官方模板 + 一张手写别名表造的，**样本量太小、难度也偏低于真实长尾**；上线前需要 30–50 份真实乱表。
3. 已用真实 Key 跑过 `--online`（5 用例、约 2.2k tokens/次、1s 左右/次），但**只跑过一次**，没有做重复性统计，温度与随机性影响未知。
4. 未做多级表头合并、合并单元格还原；表头定位是「命中同义词最多的那一行」的启发式，遇到双行表头会失手。
5. `--llm-scope unresolved` 时黑名单列不会送模型（这是设计：拦在规则层更省钱更稳），所以该模式下**没有测到模型自身的陷阱识别能力**；要测请用 `--llm-scope all`。
6. 模型输出偶发裹 ```json 围栏，`llm._parse_json()` 已做剥离，但这类防御本身说明**不能假设模型守约**。
7. **原型侧口径冲突（待定，未改）**：原型的 `checkProblems()` 把「会员编号」当**必填 error**，而 PRD §6.12 的必填清单里没有它；本 PoC 的 `field-dict.json` 按 PRD 标为非必填。所以同一条缺列，概览标「需修正」、实测明细标「非必填未命中」。**两者要统一，改哪边属于口径决定的，我没动。**

## 安全

- 本目录不含任何真实业务数据：`real_members_export` 的样本值取自仓库内既有的 `members.xlsx`。
- `DEEPSEEK_API_KEY` 从环境变量或 `.env.local` 读；`.env.local` 已写进 `.gitignore`，不进 git、不进日志。
- ⚠️ **这把 Key 在聊天里以明文传递过，建议测试完就去 DeepSeek 控制台轮换**，轮换后只改 `.env.local` 一行即可。
- `server.py` 是**本地自测桥**：默认只监听 `127.0.0.1`。用 `--lan` 会绑 `0.0.0.0`、暴露到内网，
  而它**无鉴权、无并发控制、无限流** —— 只在可信内网临时用，测完 `Ctrl+C` 停掉；
  **绝不要**把 `--lan` 用在公共 Wi-Fi 或任何能连到它的不可信网络上。
- 接生产前请把「源表上传 → 第三方 API」写进数据合规说明。
