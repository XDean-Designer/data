1.1 背景：两个断点

断点一：店开完了，没人招呼。现状实拍显示，登录 → 创建店铺多步 → 落点写死为首页，全程没有「你现在最想做什么」的询问。用户冲着获客 / 小店来，却被领进首页，目标 TAB 在第 4、第 5 个，难以主动发现；主战场转化从 320 掉到 168（流失 47.5%）（数据出处见 对标-登录入驻体验优化.html 引用的现状报告）。

断点二：老店数据进不来。现状是运营代导：线下运营把门店数据整理进官方 Excel 模板 → 核对 → 提交后台识别导入。店主本人几乎碰不到「交数据」这一步，开店后要用的会员、卡、价目长期缺位，店等于「开了但没法开单」。

1.2 目标

  • 开店不断线：登录后按「定位 → 认领 / 创建 → 确认 → 一键开店 → 分流」走完，开店成功后先问需再落点，不再直接甩到首页。
  • 数据能自助：用户自己交源（现有表 / 截图 / 照片均可），杂表交给 AI 转成官方标准表，用户在数据概览里看得见全部数据、改得动识别错处，确认后自助入库；模板从唯一入口降为稳妥旁路。
  • 失败可闭环：单行失败不阻断整批，失败明细可逐条手动补录（含补录多张老卡），补完再移除。
  • 可撤回：会员表是老店最敏感资产 —— 上传页讲清用途，结果页可整批删除回到导入前。
  • 旧账可查：历史消费单列存放，只识别日期 / 金额 / 顾客姓名供筛选搜索，不污染订单流水与经营数据；导入前明确告知需单独操作。

模块 5　交互细则 / 异常流

读者：前端 ✓ · 后端 了解 · 测试 ✓

5.1 通用

  • 返回矩阵：见 §3.2「返回 / 出边」列；子页一律返回上一级，唯一例外是补录链路 —— 从半屏进「添加卡」后，返回要回到失败明细并重开半屏（延时 240ms），而不是停在一个没有上下文的列表。
  • 整页切换：即时显隐（同一时刻只有一个 .screen.active）；「添加卡 / 补录老卡」额外加 300ms 右侧滑入 / 滑出（slideTo / slideBackTo），补录完成回跳为 260ms。
  • Toast：底部居中，单条覆盖式（后一条顶掉前一条），显示 1800ms；不阻断操作。
  • 半屏 / 弹窗：补录半屏与核对明细 Sheet 贴底、内容区最大高度 85%，内部可滚；遮罩点击即关闭（定位说明与系统权限除外，遮罩不关）。
  • 数字强调：数据概览与结果页的数量走 .num-em（加粗 + 加大一级），保证「可传 118 / 需修正 6 / 已忽略 2」在一屏里可读。
  • 滚动：每个整页为「标题栏固定 + .scroll-body 滚动 + 底部按钮固定」；内容不足时按钮仍贴底。

  • 点「确认传输」后先做前置校验：仍有未忽略的「需修正」行 → toast「还有 N 行需要修正 · 已跳到第一处」并滚到该行展开编辑，不进入仪式层；只有「建议确认」或已全部忽略才放行。
  • 放行后拉起全屏仪式层（#ceremony，见 §6.13.3）：① 正在逐行校验 → ② 校验通过，正在封存（印章旋转）→ ③ 封存完成，正在写入本店 → ④ 生成编号 RTB-YYYYMMDD-XXXX 并给出本批三行汇总。每段约 700–900ms，层内不提供取消（避免半途中断的错觉），全部完成才切结果页。

  • 结果页只回显本批三类数量（会员与持卡 126 人 / 会员卡模板 4 张 / 价目 42 项，原型造数）；分类明细抽样 10 条，卡模板全量。再导入时按模式改写为「新增 / 更新」或「已清空后写入」，并展示本店合计存量。

5.9 兜底与异常

  • 刷新丢失：原型所有引导态（pendingInvite、fabVisible、importSelection、映射确认、失败补录内容）均在内存中，刷新即回到 login（或 URL 指定的 flow）。线上是否需要断点续传 / 任务恢复【待联调确认】。
  • 直接深链到中间页：不校验前序状态（例如直接进 import-preview 也能确认导入）；仅用于评审，线上应拦截非法顺序。
  • 事件重复绑定：原型一次性 boot() 绑定，无重复；线上若采用局部重渲染，注意不要在容器上重复挂同一 handler（价目表 PRD v1.32 的「写副本」教训同理：状态写入要落到真实数据源，不要写到渲染副本）。
  • 网络 / 解析失败：原型无失败态；线上需要「解析失败 → 重试 / 换文件 / 转人工」的兜底，本期不在范围。

依赖口径：会员卡模板的项目权益与会员价必须以价目表的项目为基准，因此卡模板不能脱离价目表单独导入；价目表可以单独导入（只是价目，不涉及卡权益），逻辑上不受影响。「同批」不等于「同表」：卡模板与价目表必须在同一批次内一起提交，但必须各用一个 Excel 文件分别上传，不允许把两类字段合成一张表——上传页按类别逐类采集，转换与概览均按类别分开呈现。

多表口径：每个导入类别最多可添加 3 个 Excel 文件（会员与持卡信息 / 会员卡模板 / 价目表各自独立计数）；同一类别的多个文件合并成一批一起转，AI 按表头语义对齐同一字段（列名不必逐字相同），条数累加为概览里的行；列名差异过大导致某列识别不到时，该字段在概览里标「需修正」，不硬阻断。

演示口径：取消某一类不改变已固定类别的条数（持卡 126 人 / 卡模板 4 张 / 价目 42 项），原型只校验「至少一项」；只导持卡信息时，卡模板数量改为自动生成草案中被勾选的数量（原型聚合 10 张）。

类别图标口径：三类各用一枚 20px 线描 SVG（stroke-width 1.8、fill=none、currentColor），装在 36 × 36、圆角 10px、浅品牌底 #fff1f2 的方框里，描边色取品牌色 —— 会员与持卡信息 = 人像，会员卡模板 = 卡片，价目表 = 价签。不用灰色占位块；数据概览的分类 tab 与行首图标沿用同一套规格，保证同一类别在两处的识别符号一致。

6.11.1 转换规则（口径）

  • 不要求列名：按单元格内容、表头同义词、列内数据类型推断字段，列序任意；表头行不必在第 1 行，标题行 / 说明行会被跳过。
  • 多 sheet 合并：同一文件内的多个 sheet 按「列结构相近」合并成一批，不同结构的 sheet 分别转、条数累加。
  • 一行一张卡：官方会员模板的粒度是「卡」；原表若一行写了多张卡（如「储值余额 / 计次次数」并列），转换时拆成多行，会员编号与姓名重复填写。
  • 缺列补默认并标记：官方模板里非必填的列缺失时补空值，必填列缺失时该行标「需修正」——不整表打回。
  • 原表只读：转换结果只存在本次批次里，不回写用户原文件；副文案「原表不改」即此意。
  • 照片：识别结果同样落到标准表，转换过程对用户不可见；若某张照片整体识别失败，其行进入概览并标为需修正，而不是从批次里消失。
  • 幂等：同批重复进入本屏不重跑动画（convertDone 缓存），只有「重新上传 / 重新选择文件 / 从队列重新开始转换」才重置。

与旧版的关系：v1.x 的「确认字段对应」页在本版从主链路移除（import-map 保留为兼容深链，不进用户流程）。因此页面上不再出现类别 tab、映射进度条、「确认「X」映射关系无误」勾选与自定义字段输入 —— 这些都由转换 + 概览替代。

阶段 规格
拦截 点「确认传输」先全量复查（不只当前 tab 的可见行）：任何类别存在未忽略的 error 行 → 不进入仪式，自动切到该类、筛选置「只看问题」、展开第一条问题行并滚动定位，同时 toast「还有 N 行需修正，已跳到第一处」。不允许带着已知错误进入传输；warn 行不拦
可传输为 0 被忽略 + 需修正把可传输清零时 → toast「没有可传输的数据」，留在概览
全屏层 覆盖整个手机画布（#ceremony，近黑底 + 居中卡片，role=dialog + aria-modal）：小标「确认传输」→ 标题 → 封存印章（圆环 + 「封存」二字，封存阶段旋转）→ 三步清单 → 完成区。层内没有取消按钮，避免用户以为「可以退回去改」；要点返回时在完成区之前不可关
第 1 步 0ms：「正在逐行校验」；清单高亮「逐行校验（必填 / 格式 / 卡名称）」，前两步未完成态；印章不转
第 2 步 约 0.78s：「校验通过，正在封存」；清单第 1 步打勾、第 2 步高亮「封存本批（生成本次传输编号）」；印章环开始旋转
第 3 步 约 1.56s：「封存完成，正在写入本店」；前两步打勾、第 3 步高亮「写入本店（会员 / 卡模板 / 价目）」；印章保持完成前的旋转
完成 约 2.38s：小标改「已封存」、标题改「本批已封存」、三歩全部打勾、印章停转并加完成态；完成区出现 —— 勾号 + 「已封存并传输 N 条」+ 分类明细「会员与持卡 1,425 · 价目表 38」+ 传输编号 RTB-YYYYMMDD-XXXX（当日日期 + 4 位随机数，仅作本批标识）+ 主按钮「查看导入结果」

动效口径 转场只做「淡入 + 印章环旋转 + 步骤逐条点亮」，不做粒子 / 音效；prefers-reduced-motion 下取消旋转，仅保留步骤状态切换

设计意图：这一步是用户「把老店数据交给新店」的心理节点，仪式感的作用是让「已封存」这件事被感知到（有编号、有回执、有明确的完成瞬间），而不是装饰。因此：① 拦截必须先于仪式（不能先表演再报错）；② 编号必须落在完成区，让用户可追溯；③ 全过程不给「取消」，退出口径统一为完成后的「查看导入结果」。

8.2 会员去重

  • 优先手机号去重；同表重复导入按手机号不翻倍。
  • 无手机号仍可导入，但标「待补全」，不自动合并（避免把两个同名的人并成一个）。
  • 手机号为空 / 非法时：非法进失败明细（如 f1「手机号格式错误」），为空则入库但标待补全。
  • 线上「姓名 + 模糊手机 / 备注」的人工确认合并本期不做。

8.3 会员卡模板规则

  • 定义：模板是店铺预置的卡定义（名称 / 充值 / 赠送 / 折扣 / 权益 / 会员价 / 有效期），为会员开卡时从中选择；不是某位会员持有的卡。
  • 必须与价目表同批导入：模板的项目·产品权益与会员价以价目表项目为基准，缺价目表则无法关联。勾选「会员卡模板」时系统自动锁定并勾选「价目表」，且价目表在卡模板勾选期间不可单独取消。
  • 同批 ≠ 同表：卡模板与价目表各用一个 Excel 文件分别上传，不允许合成一张表；上传页按类别逐类采集，转换与概览按类别分开呈现，两类的列名与字段互不混用。
  • 每个类别最多 3 个 Excel：会员与持卡信息 / 会员卡模板 / 价目表各自独立计数；同类多表合并成一批转（AI 按表头语义对齐同一字段，列名不必逐字相同），条数累加为概览里的行；个别列识别不到时该字段标「需修正」，不硬阻断。
  • 价目表可单独导入：只含价格，不引用卡权益，逻辑上不受影响。
  • 自动生成（v2.0 已下线）：v1.x 会在「未导卡模板」时按「卡种」去重生成模板草案并进确认页（§6.12 留档）。v2.0 起该页从主链路移除：卡模板随队列上传（官方 5 sheet 模板），或由转换补全；卡名称在店内不存在时在数据概览标「需修正」，由用户改卡名或忽略该行。
  • 草案只生成一次：返回上游再进不重复追加；类型页改动勾选后草案与勾选结果重置（v2.0 该页已下线，见 §6.12 口径）。
  • 草案与本批绑定：整批删除时一并回滚（§8.9）。
  • 会员持有的卡：可随会员与持卡信息导入（卡种 / 有效期 / 储值余额），也可在失败补录中手工录入；卡必须挂到会员，一个会员可持任意多张，同卡种可重复，补录必须填卡内余额。
  • 补录不产生收款单据、不写订单流水；卡余额无法解析的行进失败明细，可通过补录闭环修复。
  • 原型卡片（储值 / 次卡 / 套餐）为演示数据，线上模板字段以会员卡模块为准。

8.4 价目表规则

  • 按类型列区分项目 / 产品；缺类型列时默认项目（原型明细均为项目）【待联调确认】。
  • 价格必填且为有效数字；缺失进失败明细。
  • 同名策略（合并 / 新建）需用户选择 —— 本期原型未实现，仅记录为待定规则。
  • 导入后的价目字段、分组与展示规则，以价目表 PRD 为准。

8.6 字段对齐（AI 转换取代自定义映射）

  • 不再有「自定义字段映射」：用户不需要（也无法）逐列指定源表列与标准列的对应关系；转换由 AI 完成，落点是官方标准表（§6.9.1 / §7.3 / §7.5 / §7.6）。
  • 识别依据：列名同义词（如「姓名 / 客户名 / 会员名」「卡号 / 会员卡号 / 卡编号」）+ 列内数据类型（手机号 11 位、金额小数、日期形态）+ 表头行启发（跳过标题行、合并单元格还原）。
  • 对齐不了的字段：留空并给该字段打「AI 推断 / 待补充」标记；该行若无必填缺失则仍可传输（warn），有必填缺失则标「需修正」，但不会整表打回。
  • 用户可改的只有数据，不是映射：在数据概览里逐格改值、忽略整行、删除行或新增行；改完立即重算该类全部校验。
  • 理由：老系统表头千奇百怪，让用户在手机上逐列对齐既慢又易错；把「对齐」交给 AI、把「确认」留给概览，才能既保住准确率又不卡死流程。
  • 安全边界：转换只处理本次上传文件的内存副本，不回写源文件；未识别的列不会静默丢弃，而是以「未识别 / 待补充」在概览标记（可解释性优先于自动化率）。

8.7 官方模板识别与转换规则

  • 标准口径：会员资料 24 列（一行一张卡）、卡模板 5 个 sheet、价目表 8 列，列名与列序以 §6.9.1 为准。
  • 已按官方模板填写：列名全等或同义命中 → 直接识别为对应字段，转换仅做清洗（去空格、金额去符号、日期归一、来源渠道取 1–9）。
  • 非标准表：先做表头识别与内容推断，再重排成官方列序；原表多余的列不导入（在转换结果中明示「已忽略 N 列」口径，原型以「未识别字段已标待补充」表达）。
  • 多 sheet / 多表：同结构合并、异结构分别转；同一类别最多 3 个文件，条数累加。
  • 拆行：原表一行写多张卡（余额 / 次数并列）→ 拆成多行，会员编号与姓名重复；卡级主键为会员卡号。
  • 缺列：官方模板的非必填列缺失补空并保留「待补充」标记；必填列（会员卡号 / 会员姓名 / 手机号 / 卡类型 / 卡名称 / 卡剩余价值 / 来源渠道，储值卡的充值余额）缺失 → 该行「需修正」。
  • 照片：识别结果按同一套规则转成标准表，转换过程对用户不可见；单张照片整体失败时其行仍进概览并标需修正。

8.8 失败行与补录

  • 单行失败不阻断整批；成功数照常入库，失败数在结果页明示。
  • 失败原因须可读（行号 + 原因 + 原值），支持下载失败明细 Excel（原型为 toast 演示）。
  • 手动补录只要求姓名；性别 / 手机号 / 卡可空，填了必须合法（§5.7）。
  • 一个失败会员可补多张卡；卡余额必填；不设「无卡」状态。
  • 补录后不自动移除条目，必须点「补录完成」；这样用户还能回去改。
  • 「补录完成」后条目不可恢复；要恢复只能重新导入该批。
  • 失败行重试（只重试失败行）为 P1；原型未实现。

8.9 整批删除

  • 删除范围：本次导入的会员与持卡信息 + 卡模板（含自动生成的草案）+ 价目表 + 已手动补录的条目；不删除本店原有数据。
  • 必须二次确认，正文列明数量；确认后回引导页并 toast。
  • 删除后同批不可恢复，需重新导入。
  • 原型为演示态（不真正删内存数据），线上需事务化删除并返回计数。

8.10 历史消费（只读旁路）

  • 不写入「订单流水」，写独立「历史消费」存储（LegacyOrder）；不参与开单 / 退款 / 改单 / 业绩 / 提成 / 会员余额 / 经营分析。
  • 不规定字段结构：整行原样保留（列名与列序不限）；只额外识别日期、金额、顾客姓名三项，供列表筛选与搜索。
  • 唯一入口是 Excel（含标准表头展示，无下载）：不上拍照 / OCR；理由见 §6.8 要点 ②。
  • 日期与金额必须能解析才能入库；姓名可空。解析失败行不入库，进失败明细并支持下载，不做站内补录。
  • 不做自动去重：历史账单无稳定主键，按行追加；列表已有数据再点「导入」时须半屏确认「追加」或「先整批删除再导入」。
  • 查看入口已定：工作台 → 店铺管理 →「历史订单」（列表 / 时间·金额·姓名筛选 / 独立详情）。
  • 导入前在引导与说明页明确告知：历史消费需单独导入，建议先导会员与持卡信息 / 卡模板 / 价目表；不设硬门槛。
  • 会员与持卡信息、会员卡模板、价目表可选择不同来源（Excel 或拍照，逐类独立），混合批次先拍照、后上传，结果合并展示。

8.11 分流与邀请

  • 分流只负责落点，不展开版块内承接。
  • 本期只有「我要管理店铺」与「先随便看看」产生后续（首页 + 邀请半屏）；其余三支只 toast。
  • 邀请只在「分流 → 首页」路径弹一次；跳过不影响首页任何内容。

  • 原型不做偏好持久化；线上「同账号不反复弹」由服务端记录【待联调确认】。

  • 标准表转换按批异步：端上以四步自检承载等待（约 2.48s 演示），真实服务端转换须返回进度或至少返回「已受理 + 轮询 / 回调」。
  • 导入提交须异步：端上展示进度，服务端按 500 条 / 批分片写入，失败行单独回收。
  • 大表（≥ 5 万行）解析不得阻塞端上交互；上传即返回批次 id。

11.2 安全与隐私

  • 文件仅本次导入可见，不跨门店；下载失败明细须鉴权。
  • 手机号在列表页部分脱敏展示（如 138****0000）【待联调确认】；补录页明文可编辑。
  • 上传文件不落公开桶；解析完成后按保留策略清理。

11.3 兼容与适配

  • 端上按 390 逻辑宽设计，桌面预览居中；映射表允许横向滚动。
  • iOS Safari / Android Chrome 需支持半屏 + 底部键盘避让（--kb-h）。
  • 拍照入口依赖相机权限；拒绝后回到上传路径，不得死锁。

11.4 可用性

  • 任何一步失败都要能「回来」：映射可返回、核对可返回、失败可补录。
  • 所有破坏性操作（整批删除、删卡、补录完成）都有确认或明确不可逆提示。
  • 文案不出现「导入失败」这类终局词；失败按条处理，整批仍算成功。
